How to read a request waterfall like a DevTools pro

HM
Hammad MeerPublished Sep 2, 2026 · 7 min read

Browser developers already know how to read a network waterfall. A WordPress request lifecycle waterfall uses the same visual grammar — but the phases mean something different. Here's a phase-by-phase primer.

muplugins_loaded
plugins_loaded
init
rest_api_init
rest_pre_dispatch
shutdown

muplugins_loaded

Must-use plugins load first, before regular plugins. This phase should be tiny — a handful of milliseconds. If it's large, you likely have a must-use plugin doing expensive work far earlier than it needs to.

plugins_loaded

Every active plugin's main file executes here. This phase scales roughly with plugin count, so some size is normal — but a single plugin dominating it usually means synchronous work (like an external license check) that belongs later or behind a cache.

init

Post types, taxonomies, and most plugin setup logic register here. This is one of the busiest hooks in WordPress, so look at the Hooks tab filtered to init specifically rather than judging the phase as a block.

rest_api_init / rest_pre_dispatch

Only present on REST requests. This is where route registration and permission callbacks run — a spike here (like the amber bar above) is a strong signal to open the Hooks tab and look for a permission callback doing a database or remote call on every single request.

template_redirect / the render phase

On front-end page loads (not shown above, since this example is a REST call), this is where the theme actually queries and renders content. Page builders and heavy widget logic tend to show up here as a wide phase with many nested database sub-bars.

shutdown

Runs after the response has already been sent in most cases — logging, cache warming, deferred jobs. It should almost never be large enough to affect perceived response time, but a bloated shutdown hook can still hold a PHP worker busy longer than necessary under load.

Shapes worth recognizing

  • One clearly dominant phase — the normal, easy case. Deep-link into it and look at queries or hooks for that phase specifically.
  • Many small, evenly-sized phases — often means death by a thousand cuts: lots of plugins each doing a little bit of work. Harder to fix with one change; look for the few worst offenders in the Hooks tab across the whole request.
  • A late spike with nothing obviously heavy before it — check the HTTP API tab; this shape is a classic sign of a blocking outbound HTTP call.
