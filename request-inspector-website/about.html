About

Built to answer one question, properly.

"What is this request actually doing?" — asked on enough client sites that it turned into a plugin.

The problem

Debugging a slow or misbehaving WordPress site usually means switching between four tools: a query profiler for the database, a hook inspector for plugin conflicts, a browser network tab for the actual HTTP traffic, and an error log for the PHP side. None of them share context, so you end up mentally stitching a timeline together from four unrelated screens.

The approach

WordPress Request Inspector takes the two things that already work well elsewhere — Query Monitor's deep WordPress execution context, and Chrome DevTools' request/response/waterfall model — and combines them into one native wp-admin panel. A single request opens into nine tabs: Overview, Request, Response, Headers, Database, Hooks, HTTP API, PHP, and Timeline. Everything about that request lives in one place.

Who it's for

  • Plugin and theme developers who need to see precisely how their code executes across REST endpoints, AJAX handlers and template rendering.
  • Agency engineers and SREs auditing third-party plugin performance or chasing a TTFB regression on staging or production.
  • Enterprise DevOps teams who need strict redaction, role-based access, and a guaranteed low runtime overhead before profiling is allowed anywhere near a live cluster.

What it isn't

It isn't an external APM, and it doesn't send your data anywhere. Everything is captured and stored inside your own WordPress database, self-hosted, under your own retention and redaction rules.
