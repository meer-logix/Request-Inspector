A practical method for debugging slow WordPress requests

HM
Hammad MeerPublished Aug 28, 2026 · 9 min read

"The site feels slow" is not a debugging starting point — it's a symptom. Here's the process I use to go from that vague complaint to an actual root cause, using the Timeline, Database and Hooks tabs together instead of guessing.

Step 1: Reproduce it inside a captured request

Turn recording on, set sampling to 100% capture temporarily (switch back to "slow & errors only" once you're done), and reproduce the slow page load or API call. You want one specific request row in the Explorer to anchor the rest of the investigation — not an average.

Step 2: Start at the Timeline tab, not the Database tab

It's tempting to jump straight to SQL, but most regressions are lifecycle-shaped, not query-shaped. Open the Timeline tab and look at which phase — plugins_loaded, init, rest_api_init, template_redirect — is disproportionately large relative to the others.

A healthy request usually has one dominant phase relative to page complexity. If two unrelated phases are both unusually large, you likely have two separate problems, not one.

Step 3: Deep-link into the slow phase

Click the oversized segment. Request Inspector surfaces "Jump to Database Tab" and "View Caller Backtrace" links scoped to just that phase — so instead of scanning all 214 queries for the whole request, you're looking at the dozen that ran during rest_api_init specifically.

Step 4: Check for duplicates before chasing duration

In the Database tab, sort by duration, but glance at the duplicate-query badges first. A query that runs in 4ms but fires 40 times inside a loop often costs more, in aggregate, than a single 180ms query — and is usually a cheaper fix (add a cache, hoist the query out of the loop).

// Duplicate query pattern — usually a loop problem foreach ( $product_ids as $id ) { $meta = get_post_meta( $id, '_price', true ); // N+1 } // Fix: prime the cache once update_meta_cache( 'post', $product_ids );

Step 5: If it's not the database, check Hooks

If query time looks normal but the phase is still slow, open the Hooks tab filtered to that lifecycle stage. Look for callbacks flagged amber (>5ms) or red (>20ms) — third-party plugins doing synchronous HTTP calls or heavy computation inside a hook are a common culprit here, and the inline backtrace tells you exactly which plugin to report the issue to.

Step 6: Check the HTTP API tab for outbound calls

External API calls — payment gateways, analytics, license checks — routinely hide inside init or wp_loaded and block the response. The HTTP API tab lists every outbound wp_remote_* call with duration, so a slow third-party endpoint is visible instead of masquerading as "WordPress is slow."

Step 7: Confirm the fix with a second capture

After the fix, reproduce the same request again and compare the new Timeline against the original. Because both are stored, you can view them side by side rather than trusting memory of "it feels faster now."

A short checklist

  • Reproduce inside one captured request, not an aggregate.
  • Start at the Timeline tab to find the disproportionate phase.
  • Deep-link from that phase into Database or Hooks — don't scan everything.
  • Check duplicate-query badges before chasing single-query duration.
  • Check the HTTP API tab for blocking outbound calls.
  • Re-capture after the fix and compare against the original.
