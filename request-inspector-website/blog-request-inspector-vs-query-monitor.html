WordPress Request Inspector vs. Query Monitor: the full comparison

HM
Hammad MeerPublished Aug 20, 2026 · Updated Sep 10, 2026 · 12 min read

Query Monitor has been the default WordPress debugging plugin for years, and for good reason — it's fast, thorough, and free. So the honest question isn't "which one is better," it's "which gaps does each one leave, and does that matter for what you're doing?" This is a straight comparison, including the places Query Monitor still wins.

The short version

Query Monitor is excellent at showing you WordPress's internal execution — hooks, queries, conditionals, template files. What it doesn't show you is the actual HTTP request and response — the JSON body a REST endpoint received or returned, formatted and readable, the way a browser's network tab would show it. That's the specific gap Request Inspector was built to close, alongside a full request/response redaction layer and a DevTools-style waterfall.

Where Query Monitor still wins

Query Monitor is deliberately request-scoped and lightweight: nothing persists after the page loads, so there's effectively zero configuration and no storage to manage. If you just want a fast "what happened on this one page load" panel while actively coding, that simplicity is a real advantage, and its install base means almost every WordPress developer already knows its UI.

Where Request Inspector adds capability

1. The response body is not an afterthought

When you're debugging a REST endpoint or an external API integration, the actual JSON that came back matters as much as which queries ran. Request Inspector's Response tab shows formatted, syntax-highlighted request and response bodies with headers, byte counts, and a "Save as Fixture" action — closer to a browser's network tab than a WordPress debug bar.

2. A real timeline, not just totals

The Timeline tab draws a millisecond-accurate Gantt chart across the WordPress lifecycle — muplugins_loaded through shutdown — with zoom controls and the ability to click a phase and jump straight into the Database or Hooks tab for that slice of time. That's a materially different way of finding "where did 300ms go" than reading a flat list of totals.

3. Redaction is the default, not a manual step

Because Request Inspector persists data (even briefly), it treats redaction as a first-class requirement: Authorization headers, passwords, tokens, cookies and nonces are masked in memory before anything is written to storage. Query Monitor, being request-scoped and non-persistent, doesn't need this in the same way — but it also doesn't give you the option to keep history for later comparison.

4. Built for handing off to someone else

An IP allowlist, a manage_options capability gate, and an immutable audit log mean an agency can safely enable it on a client's production site, gate exactly who can see captured data, and prove who looked at what — much closer to what enterprise DevOps teams expect from a profiling tool.

Can you run both?

Yes. They don't conflict — Query Monitor still gives you the fast, disposable per-page-load panel, while Request Inspector's stored history means you can compare a slow request against yesterday's baseline, or capture an intermittent bug you can't reproduce on demand.

How to decide

Choose Query Monitor if you want the lightest possible always-on debug bar for active local development, with no persistence to manage.

Add Request Inspector if you need to see actual request/response payloads, want a waterfall view of a full page lifecycle, need to profile safely on staging or production with redaction and access control, or want to hand a captured request to a teammate instead of describing it from memory.
